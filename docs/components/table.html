02 // Composition

Built from Tabs

The header's tab switcher is the same <Tabs> pattern documented separately.

TableWidget's optional header-right tab switcher is built directly on the standalone <Tabs> component (size="sm") — this is in fact where the vs-segment-control pattern was first formalized from, and TableWidget was refactored afterward to render <Tabs> internally instead of duplicating the markup, so there is now exactly one implementation of this pattern.

Correction: an earlier pass here assumed the admin panel's DataTables usage needed new per-page JS to wrap, and skipped a Blade component on that basis. Re-auditing public/vendor/admin/js/app.js directly found that assumption was wrong: a single global script already auto-selects every .datatable / .datatable2 table on the page and initializes DataTables itself (shared language strings, pageLength 50, pagination styling) — no per-page script exists or is needed. That makes it a genuine thin markup wrapper, same as vs-pagination.blade.php, so vs-table.blade.php was built after all.

Usage — Blade

<x-vs-table :columns="[['label' => '#', 'width' => '2x'], ['label' => 'Name', 'width' => '7x'], ['label' => 'Views', 'width' => '3x']]"> @foreach ($categories as $category) <tr> <td>{{ $category->id }}</td> <td>{{ $category->name }}</td> <td>{{ $category->views }}</td> </tr> @endforeach </x-vs-table>

Row markup is written by the caller (@foreach, same as every real page today) — badges, dropdown actions and icons vary too much per page for the component to generalize further; <x-vs-table> only owns the card chrome, the real table.datatable class, and the header row.

Props — Blade

PropValues
columnsarray of { label, width? } — width maps to the real tb-w-{N}x utility classes
variant'datatable' (default sort desc on col 0) | 'datatable2' (DataTables' own default order) — matches the site's two real configured variants
cardboolean, default true — wraps in the real .card chrome
