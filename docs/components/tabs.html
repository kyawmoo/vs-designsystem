Components // Tabs

Tabs

Navigation between related content panels on one page: primary tabs for major sections, secondary tabs for sub-sections. Implemented in react/src/components/Tabs.tsx (variant="primary" / "secondary" with TabPanel). The pill-shaped switch that used to be exported as Tabs is now its own component, SegmentedControl; see section 06 for when to use which.

Primary tabs change what the page shows; they do not filter it. The selected tab has aria-selected="true" and its panel is the only one visible. The same value drives both, so the two never disagree.

06 // Tabs vs SegmentedControl

Tabs vs SegmentedControl

Two patterns, two jobs. Do not swap them.

The rule

When I pick an option, does the page show a different part of the content, or the same content arranged differently?

Different part → TabsEach option has its own panel. Choosing one swaps the content below.
Same content → SegmentedControlChoosing one re-sorts, filters or re-scopes what is already there.

Renamed (6 Oct 2026): the React component that was exported as Tabs is a segmented control (it selects one option or filter; it does not switch content panels), so it is now SegmentedControl (types SegmentedControlProps, SegmentedControlItem). Same classes, same output. <Tabs> with no variant still renders it, as a deprecated alias, so the reports dashboard keeps working until it switches. New segmented switches use SegmentedControl; new tab navigation uses <Tabs variant="primary"> or "secondary".

The existing segmented pattern, as documented before

React (vs-segment-control / vs-segment-button) is a single bordered track with a solid brand-primary fill on the active tab — already live in the reports dashboard's TableWidget and several views. Blade (.tabs-custom .nav-pills) is individually bordered pills with gaps, no shared track — the main site's own existing CSS, in production. Deliberately not unified: that would mean changing pages that already work correctly today. The underline primary / secondary variants are React only; a Blade equivalent is not part of this change.

07 // Guidelines

Do’s and Don’ts

Short labels, two levels at most, tabs for content, not for filters.

DOUse primary tabs for the few major sections of one page; keep labels to 1–2 words.
DON’TDon’t write long, sentence-like labels or squeeze in more than about 6 tabs.
DOUse secondary tabs for sub-sections of the selected primary tab; the two levels read differently.
DON’TDon’t add a third tab row. Use a local side list or a sidebar for the third level.
DOUse Tabs when each option shows a different panel of related content.
DON’TDon’t use Tabs as a compact filter or sort switch. That is a SegmentedControl.
DOShow a count with a Badge when it helps people choose the tab. Use one tone for all counts.
DON’TDon’t style tabs as pills or buttons. The underline is what marks them as tabs.
08 // Accessibility

Accessibility & Keyboard

WAI-ARIA tabs pattern, automatic activation.

KeyBehaviour
TabMoves into the tab list onto the selected tab (the only tab in the page tab order), then out to the tab panel.
→ / ←Focus moves to the next / previous enabled tab and selects it. Wraps from last to first and back. Disabled tabs are skipped.
Home / EndFirst / last enabled tab, selected.
Enter / SpaceSelect the focused tab (each tab is a real <button>).
Alt / Ctrl / ⌘ + arrowsIgnored, so browser shortcuts (for example Alt+← back) keep working.
RequirementHow it is met
Roles and relationshipsList role="tablist"; tab role="tab" with aria-selected; panel role="tabpanel" with aria-labelledby → its tab. Pass id to Tabs and the same value as tabsId to each TabPanel to add aria-controls. Without id there is no aria-controls (never a dangling reference).
Accessible nameGive the list a label (aria-label), especially when a page has two tab lists. A badge becomes part of the tab’s name (“Products 24”); icons are aria-hidden.
Selected is not colour-onlySelected tab = darker text and a 2px indicator; the state is also exposed as aria-selected.
Contrast (WCAG 2.2 AA)Unselected text --vs-color-text-body 14.2:1; selected text --vs-color-text-heading 18.1:1; primary indicator --vs-color-brand-primary-text 5.2:1 (needs 3:1); focus ring 15.9:1 (needs 3:1). --vs-color-text-muted (2.8:1) is used only for disabled tabs, which are exempt.
Focus visibility2px ring from the focus-ring tokens, drawn inside the tab because the list scrolls and would clip an outer ring. The panel has its own ring.
DisabledA real disabled button: not focusable, not clickable, skipped by arrows.
MotionOnly a 150ms colour transition; removed under prefers-reduced-motion.
TouchPrimary tabs are about 48px tall. Secondary tabs grow from about 36px to 44px on touch screens (pointer: coarse).
DirectionHorizontal, left-to-right only. Right-to-left layouts are not handled (arrow keys are not mirrored).

Not verified: real screen readers (NVDA, VoiceOver, TalkBack). The ARIA structure follows the WAI-ARIA Authoring Practices tabs pattern and is covered by automated tests, but spoken output has not been listened to.

09 // Responsive

Desktop, Tablet & Mobile

One row always; overflow scrolls sideways.

Desktop · 1200px and up · all tabs visible, content-width
Tablet · about 768px · same tabs, tighter page margins
Mobile · 320–480px · one row, scrolls sideways

Tabs never wrap onto a second row (that would look like two levels). When they do not fit, the tab list scrolls horizontally and moving focus with the arrow keys scrolls the focused tab into view. Keep labels short and the count low so scrolling stays the exception, and do not rely on a hidden scrollbar.
