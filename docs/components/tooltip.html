Components // Tooltip

Tooltip

A short, supplementary hint for a control, shown on hover and keyboard focus. Implemented in react/src/components/Tooltip.tsx. It describes a control; it never replaces its name, and nothing essential may live only in a tooltip.

07 // Accessibility

Accessibility, Keyboard, Screen Reader & Touch

WAI-ARIA tooltip pattern · WCAG 1.4.13.

InputBehaviour
Pointer hover (mouse, pen)Opens after 300ms. Closes 100ms after the pointer leaves the trigger and the tooltip, so the pointer can move onto it (hoverable).
Keyboard focusOpens immediately on :focus-visible. Focus stays on the trigger; the tooltip is never focusable and Tab moves on to the next control. Blur closes it.
EscCloses it without moving focus or the pointer (dismissible).
Pressing the controlCloses it so it never covers the action, and it does not reopen until the pointer leaves and returns.
TouchNot shown. A tap must perform the control’s own action, and long-press is unreliable across browsers. So nothing essential may exist only in a tooltip; the screen-reader description below is unaffected.
Screen readerThe trigger has aria-describedby pointing at a visually hidden role="tooltip" element holding the same text. It is always in the page, so the description is read on focus whether or not the visual tooltip is showing. The visible copy is aria-hidden to avoid reading it twice.
Accessible nameThe tooltip describes; it never names. An icon-only control must carry its own aria-label (or visible text).
ContrastText 15.9:1 on the surface; surface 15.9:1 against a white page (needs 3:1 for UI).
MotionA 120ms fade only; none under prefers-reduced-motion.
PersistentStays until pointer or focus leaves, Esc or press (it does not time out).

Disabled controls. Browsers do not reliably send hover or focus to a disabled button, so a tooltip on one is not dependable. Explain why it is disabled in visible text instead.

Not verified: real screen readers (NVDA, VoiceOver, TalkBack) and real touch devices. Behaviour is covered by automated tests and checked in desktop Chromium only.

08 // Responsive & Edges

Responsive & Viewport-Edge Behaviour

The frames below act as small viewports.

top → bottomno room above the trigger
bottom → topno room below the trigger
left → rightno room on the left
right → leftno room on the right
slides along the edgearrow still points at the trigger
narrow viewportleft/right fall back to top/bottom
SituationBehaviour
Preferred side has no roomFlips to the opposite side; if that has no room either, tries the two other sides, then takes the roomiest.
Near a left/right edgeSlides along the edge to stay 8px inside the viewport; the arrow keeps pointing at the trigger’s centre.
Page or container scrolls, window resizesRepositions while open.
Clipping parents (overflow: hidden, scroll areas, modals)Not clipped: the tooltip lives in a portal on document.body.
Phones (≈ 320px)Width is capped at 100vw − 16px; left/right fall back to top/bottom when they cannot fit.
Long textWraps at 240px; unbroken strings break anywhere. Keep it short anyway.
